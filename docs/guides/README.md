# 里程碑 Guide 索引与编写规范

> 每个里程碑一份 guide，记录**怎么做、注意什么、做到哪了**。里程碑划分与验收标准的来源是 [roadmap.md](../roadmap.md)，guide 是它的执行细化。

## P1 文档分工

三类文档职责不重叠，写之前先确认内容该落在哪里：

| 文档                        | 回答的问题                                                       | 时效                       |
| --------------------------- | ---------------------------------------------------------------- | -------------------------- |
| [roadmap.md](../roadmap.md) | **什么时候做什么**：里程碑划分、依赖、验收标准                   | 全程稳定                   |
| `guides/Mn-*-guide.md`      | **这个里程碑怎么落地**：分步操作、代码片段、踩坑记录、进度       | 里程碑期内活跃，完成后归档 |
| `dev/{包}/development.md`   | **日常怎么开发**：环境、命令、目录约定、编码规范、调试、常见问题 | 长期维护，随迭代更新       |

判断标准：**做完这个里程碑就不会再看的内容进 guide，之后每天都要翻的内容进 development.md。**

## P2 Pn.n 结构规范

所有 guide 与开发文档统一使用 `Pn` / `Pn.x` 两级编号，便于在对话、commit message、issue 里精确指代（例如「P2.3 那步的 tsup 配置改了」）。

### P2.1 层级定义

| 层级   | Markdown              | 承载内容                                                                         |
| ------ | --------------------- | -------------------------------------------------------------------------------- |
| `Pn`   | `## Pn 〈主题〉`      | 该主题的**主要内容**：要交付什么、为什么需要、依赖哪个 P。一到两段说清，不写细节 |
| `Pn.x` | `### Pn.x 〈子标题〉` | **细节**：开发步骤、实现要点、注意事项、进度                                     |

### P2.2 Pn.x 的固定骨架

每个 `Pn` 下的子节按此顺序展开，中间的实现类子节数量不限：

| 位置                   | 子节                           | 内容                                                   |
| ---------------------- | ------------------------------ | ------------------------------------------------------ |
| 第一个                 | 开发内容                       | 要创建/修改的文件清单、要执行的命令、分步操作          |
| 中间若干               | 实现要点 / 配置说明 / 注意事项 | 关键代码、参数选择理由、容易做错的地方、明确的禁止事项 |
| **最后一个（必须有）** | 验收与进度                     | 勾选清单 + 状态标记                                    |

开发文档（`development.md`）没有进度概念，最后一个子节改为**自检清单**——写完一段代码自己对照勾一遍，其余规则相同。

### P2.3 进度标记

每个 `Pn` 的最后一个子节固定为「验收与进度」，用统一的状态词：

| 状态   | 含义                               |
| ------ | ---------------------------------- |
| 未开始 | 尚未动工                           |
| 进行中 | 已开始，未满足全部验收项           |
| 已完成 | 全部验收项勾选通过                 |
| 阻塞   | 有外部依赖未就绪，必须写明阻塞原因 |

每份 guide 的最后一个 `P` 固定是**里程碑验收与进度总表**，汇总所有 `Pn` 的状态，作为里程碑能否收尾的唯一依据。

### P2.4 编写约定

- **写可执行的动作，不写形容词。** 「把构建修好」不合格，「三个 tsup 配置都改 `clean: false`，在 `build` 脚本里先跑 `scripts/clean-dist.mjs` 再跑 tsup」才合格。
- **代码片段给能跑的最小完整版本**，不给伪代码；不确定的地方标 `TODO(Mn)` 并说明何时补。
- **踩坑当场记录。** 调试超过 30 分钟的问题，在对应 `Pn.x` 里写清现象、原因、解法——这是 guide 最有价值的部分，也是唯一无法从设计文档推导出来的内容。
- **契约变更不写在 guide 里。** 公开 API、options 字段、CSS 自定义属性、`exports` 子路径的变更改各包 README 与 `development.md` 的对应节，guide 只引用不复制，避免两处漂移。
- **性能与浏览器兼容结论必须来自实测**（Playwright、CDP、真机），源码推断只能作为待验证假设写进 guide，并标明「未测」。
- 里程碑完成后在 guide 顶部标注「已完成」与完成日期，不删除内容——踩坑记录对后续里程碑仍有价值。

## P3 大里程碑的拆分规范

单文件超过一定体量后，查一个点要滚过大段无关内容，diff 也没法 review。**超过下面体量的里程碑必须拆。**

### P3.1 拆分触发条件

满足任意一条就拆：

| 条件                      | 说明                                                 |
| ------------------------- | ---------------------------------------------------- |
| 预计超过 800 行           | 单文件的阅读与 diff 成本开始失控                     |
| 跨两个以上包              | core 与 react / vue 的读者不同，混在一起两边都要跳读 |
| 某个 `Pn` 自身超过 200 行 | 这个 `Pn` 已经是一个独立主题，不该寄居在别人家里     |

不满足就不要拆。「一份文件从头读到尾」的形态对小里程碑更省事，为拆而拆只会增加跳转。

### P3.2 拆完之后谁装什么

拆分沿用 `Pn` / `Pn.x` 的天然分界，**不发明新层级**：

| 文档                             | 装什么                                                                                                          |
| -------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| `guides/Mn-*-guide.md`（主文档） | 全部 `Pn` 的**主要内容**：这个 P 交付什么、为什么需要、依赖谁、验收口径；外加里程碑级的范围、执行顺序、进度总表 |
| `Mn-Pn-*-{包}.md`（分文档）      | 该 `Pn` 的全部 `Pn.x`：开发步骤、代码、实现要点、注意事项、验收与进度                                           |

主文档因此始终能一屏看完全貌，**它是唯一的进度事实来源**；分文档负责深度。主文档里每个 `Pn` 末尾给一行到分文档的链接，分文档顶部反向链回主文档。

没被拆出去的 `Pn`（比如十几行的配置变更）就留在主文档里，`Pn.x` 直接展开。**不要求全拆或全不拆。**

编号不变，标题层级下移一级：`Pn.x` 在主文档里是 `### `，在分文档里升为 `## `——分文档的 H1 是它自己的标题，没必要为了对齐层级多套一层。

### P3.3 命名与落位

```
Mn-Pn-functionName-{包}.md
```

| 段             | 取值                                                  |
| -------------- | ----------------------------------------------------- |
| `Mn`           | 里程碑号，`M5`                                        |
| `Pn`           | 与主文档中的 `Pn` 编号**严格一致**                    |
| `functionName` | 该 P 的功能主题，kebab-case，两到三个词               |
| `{包}`         | `core` / `react` / `vue`，与 `packages/` 下的目录同名 |

**分文档放进对应包的文档目录，不放在 `guides/`。** 也就是 `docs/dev/core/M6-P3-focus-follow-core.md`，不是 `docs/guides/M6-P3-focus-follow-core.md`。

这么定的理由：改 core 的时候，手边要开的是 `dev/core/development.md` 和 core 的 README；把执行文档放在同一目录，一次 `ls` 就能看到这个包的全部上下文，而 `guides/` 保持为「里程碑主文档的索引」，不会随里程碑增多膨胀成几十个文件的平铺列表。

文件名前缀带 `Mn-` 保证了它们在目录里自然聚成一簇，也一眼能看出哪些是阶段性文档（里程碑结束后归档）、哪些是长期文档（`development.md`）。

跨包或不属于任何包的 `Pn`（仓库设置、CI、发布流程）不拆，留在主文档里。

### P3.4 拆分后的维护约束

- **进度只在主文档的总表里维护一份。** 分文档的「验收与进度」只勾自己的清单，状态词以主文档为准，避免两处打架。
- **分文档之间不互相深链。** 需要引用别的 `Pn` 时链到主文档的对应锚点，由主文档转发——否则改一次拆分结构要修一圈交叉链接。
- 里程碑结束时，主文档和全部分文档一起标「已完成」，不删除。
- 分文档同样遵守 P2.4：契约不复制，只引用各包 README 与 `development.md`。
